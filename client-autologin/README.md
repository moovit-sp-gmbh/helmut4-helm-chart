# client-autologin

Init container for the chart's optional Linux clients (`linuxClients` in
[../helmut4/values.yaml](../helmut4/values.yaml)).

The Helmut4 Linux client authenticates from a `helmut.auto.login` file that is normally
generated by hand, per node, from the Users menu. That does not survive autoscaling: every
replica of a Deployment would present the same identity. This image claims a *free* user from a
pool on startup and generates that user's autologin file, so client pods stay interchangeable
and an HPA can scale them.

On start it:

1. logs in as the admin account (`POST /auth/login/body`, JWT from the `Authorization` header);
2. lists users matching `USER_PREFIX` (`GET /users/search/{prefix}`) and keeps the ones with
   `isConnected: false`;
3. picks one at random — after a jitter sleep, and with a bounded retry — so replicas starting
   together do not race onto the same slot;
4. generates that user's autologin file (`POST /users/autologin/generate/{id}`) and writes it to
   `AUTOLOGIN_PATH`, an `emptyDir` the client container mounts.

An exhausted pool exits non-zero: the pod stays in `Init:CrashLoopBackOff` with the reason in its
log, which is the licensed-seat limit surfacing rather than a bug.

## Environment

| Variable | Source | Default |
|---|---|---|
| `MCC_USERS_URL`, `MCC_STREAM_URL`, `MCC_IO_URL` | `service-config` ConfigMap (`envFrom`) | — |
| `USER_PREFIX` | `linuxClients.types.<type>.userPrefix` | — |
| `ADMIN_USERNAME`, `ADMIN_PASSWORD` | `linuxClients.adminCredentials` Secret | — |
| `AUTOLOGIN_PATH` | chart | `/autologin/helmut.auto.login` |
| `CLAIM_RETRIES` | `linuxClients.claimRetries` | `10` |
| `CLAIM_RETRY_DELAY` | chart | `10` |
| `CLAIM_JITTER_SECONDS` | `linuxClients.claimJitterSeconds` | `15` |

The three endpoint URLs are read straight from the ConfigMap the chart already renders, so the
autologin file always points at the deployed release — there is nothing to configure.

## The WebSocket URL in the generated file

The generated file is base64 and decodes to a single line:

```
wss://localhost:8881/ws?token=Bearer%20<jwt>
  &userEndpoint=…&streamEndpoint=…&ioEndpoint=…
```

The three `*Endpoint` values are exactly what we send, but the `wss://localhost:8881/ws` prefix
is produced server-side and is not influenced by the request body — a file downloaded from the
Users menu carries the same prefix, since the endpoint accepts only those three fields. The
chart meanwhile routes `/v1/ws` to `users:8000`, and that endpoint is live.

So the client appears to derive its socket from `userEndpoint` rather than using that literal
host; a client on any machine other than the Helmut server could not connect otherwise. If a
client pod starts but never appears as connected in the Users menu, this is the first thing to
check — `kubectl logs <pod> -c client-<type>` will show the socket it actually dialled.
