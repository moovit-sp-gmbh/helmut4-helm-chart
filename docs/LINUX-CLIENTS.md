# Linux Clients

## Overview

The Helmut4 Linux client (`mcp_hc`) is a headless render node: it opens no port, pulls jobs over
AMQP and writes results to the shared storage. This chart can run it as an optional component,
with several **types** side by side — different mount points, different sizing, different pools
of users — each scalable by its own HPA.

A client normally authenticates from a `helmut.auto.login` file generated by hand, from the
Users menu, for one machine. That does not survive replication: every replica of a Deployment
would present the same identity. So each pod here runs an initContainer that claims a *free*
render-node user at startup and generates that user's autologin file into an `emptyDir` the
client then reads. Pods stay interchangeable, and scaling becomes a matter of having enough
users and enough licence seats.

Adobe-dependent nodes do not work on Linux; non-Adobe workflows behave as on Windows and macOS.

## Prerequisites

1. **A pool of render-node users**, created in the Helmut UI (Users → new user → *Render Node*).
   The chart does not create them — they consume licensed seats. Name them with a shared prefix
   and a counter:

   ```
   linux-render-01, linux-render-02, … linux-render-08
   ```

   No prefix may be a prefix of another type's, or the two types will claim from each other's
   pool. `linux-render-` and `linux-transcode-` are fine; `render-` and `render-gpu-` are not.

2. **A Helmut admin account** for the initContainer. It is used only to list the pool and
   generate autologin files; the client container never sees it.

3. **Concurrent-client licence seats.** `GET /v1/license` reports `license_count`. Every
   connected UI session occupies one too, so the real ceiling for a type is
   *free seats*, not just pool size.

4. **metrics-server**, if you want autoscaling — the HPA reads CPU from it.

## Minimal setup

Create the admin Secret out of band so the password never lands in your values file:

```bash
kubectl -n helmut4 create secret generic helmut-client-admin \
  --from-literal=username=admin \
  --from-literal=password='…'
```

```yaml
linuxClients:
  enabled: true
  adminCredentials:
    existingSecret: "helmut-client-admin"   # keys: username / password
  types:
    render:
      userPrefix: "linux-render-"
      replicas: 2
      appMounts: true          # mount every global.storage.volumes entry with appMount: true
```

```bash
helm upgrade --install helmut4 ./helmut4 -f install-values.yaml
kubectl -n helmut4 get pods -l app=client-render
```

Each pod produces two containers' worth of log. The initContainer says which user it took:

```
claim-autologin: claiming user 6603d6df04348000010262d1 (4 free for prefix 'linux-render-')
claim-autologin: wrote /autologin/helmut.auto.login
```

and the client should reach the users service:

```
HCWebsocketClient : Websocket connected to: ws://users:8000/v1/ws?…&autologin=true
```

The user then shows as connected in the Users menu.

## Storage

Mounts are additive. `appMounts: true` reuses the volumes the microservices already get — every
`global.storage.volumes` entry with `appMount: true`, at its own `mountPath`. On top of that,
`volumes` mounts any existing PVC wherever you like:

```yaml
global:
  storage:
    volumes:
      - name: helmut-storage
        mountPath: "/Volumes/Helmut"
        source: "//10.0.0.201/RAID/HELMUT"
        size: "100Gi"
        appMount: true
      - name: proxies
        mountPath: "/Volumes/Proxies"
        source: "//10.0.0.201/RAID/PROXIES"
        size: "500Gi"
        appMount: false          # not wanted by the microservices

linuxClients:
  types:
    transcode:
      userPrefix: "linux-transcode-"
      appMounts: true            # /Volumes/Helmut
      volumes:                   # plus the proxy share, clients only
        - name: proxies
          claimName: proxies-pvc
          mountPath: "/Volumes/Proxies"
```

A PVC is created for every entry in `global.storage.volumes` regardless of `appMount`, so
`proxies-pvc` exists even though no microservice mounts it. Paths under `/Volumes` match what
the Helmut stream nodes expect — the upstream compose file binds the host's `/mnt` to
`/Volumes` for exactly this reason.

## Autoscaling

Off by default. Enable it globally and override per type:

```yaml
linuxClients:
  autoscaling:
    enabled: true
    minReplicas: 1
    targetCPUUtilizationPercentage: 70
  types:
    render:
      userPrefix: "linux-render-"
      autoscaling:
        maxReplicas: 8         # <= free users AND free licence seats
    ingest:
      userPrefix: "linux-ingest-"
      autoscaling:
        enabled: false         # this type stays at `replicas`
        # per-type false wins over the global true
```

Three things to know before turning it on:

- **`maxReplicas` is bounded twice** — by the number of users matching the prefix, and by free
  licence seats. A pod that cannot claim a user fails its init and crash-loops; a pod that
  claims one but exceeds the licence stays `Running` while the server refuses it.
- **Scale-down interrupts work.** Kubernetes chooses the victim; a client rendering at that
  moment is sent SIGTERM regardless. `terminationGracePeriodSeconds` (default 300) is all that
  stands between it and SIGKILL. For long jobs, leave autoscaling off and size the Deployment.
- **CPU requests are mandatory.** HPA measures utilization as a percentage of the request.
  `linuxClients.resources` provides a default so this cannot be forgotten; if you override
  `resources` per type, keep a CPU request in it.

Rollouts use `maxSurge: 0` deliberately, so an upgrade never needs more users than replicas —
the old pod releases its user before the replacement claims one.

## How a pod claims its user

The initContainer image lives in [`client-autologin/`](../client-autologin/) in this repo and is
published to `ghcr.io/moovit-sp-gmbh/helmut4-client-autologin`. On start it:

1. logs in as the admin (`POST /v1/members/auth/login/body`, JWT from the `Authorization` header);
2. lists users matching `userPrefix` (`GET /v1/members/users/search/{prefix}`) and keeps those
   with `isConnected: false`;
3. picks one **at random**, after a jitter sleep and with a bounded retry — a pod only reports as
   connected once the client attaches, so replicas starting together would otherwise race onto
   the same user;
4. generates that user's autologin file (`POST /v1/members/users/autologin/generate/{id}`) and
   writes it to the shared `emptyDir`.

The endpoints written into that file come from the `service-config` ConfigMap the chart already
renders — `http://users:8000/v1/members` and friends — so clients talk to the services directly
and never traverse the ingress. There is nothing to configure and nothing to keep in sync.

## Troubleshooting

The client opens no port, so the chart defines no probes: a refused pod still reports `Running`.
Always read both containers.

```bash
kubectl -n helmut4 logs <pod> -c autologin
kubectl -n helmut4 logs <pod> -c client-<type>
```

| Symptom | Cause and fix |
|---------|---------------|
| `Init:CrashLoopBackOff` — `no free user for prefix … pool exhausted` | every matching user is connected. Add users, or lower `maxReplicas`/`replicas`. |
| `Init:` error on login | wrong `adminCredentials`, or the users service is not up yet — the pod retries on its own. |
| `Running`, `Websocket close: 1002` right after `HCWebsocketClient … connected to` | the server refused the session; almost always the concurrent-client licence. Check `license_count` and how many UI sessions are open. |
| `Running`, no `HCWebsocketClient` line at all | endpoints are wrong. Check `service-config` and what the initContainer wrote. |
| HPA shows `<unknown>` for the CPU target | no CPU request on the container, or metrics-server is not installed. |
| Two types stealing each other's users | one `userPrefix` is a prefix of the other. Rename. |

`wss://localhost:8881/ws` in the client log is expected — that is the client's *own* loopback
socket (it runs a Tomcat on 8881/8880 and connects to itself first), not the Helmut server.
The real connection is the `ws://users:8000/v1/ws` line.
